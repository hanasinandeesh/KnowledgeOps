1. OBJECTIVES OF PEER CODE REVIEW
---------------------------------
Peer code review is our primary technical quality gate at Acme Technologies. Rigorous reviews serve four objectives:
- Validate architectural design, correctness, algorithmic efficiency, and long-term maintainability.
- Prevent security vulnerabilities, injection flaws, and data leaks before software reaches staging environments.
- Foster collective code ownership, knowledge diffusion, and engineering mentorship across team members.
- Maintain uniform adherence to language-specific coding standards and architectural principles.

2. REVIEW CHECKLIST AND AUTOMATED QUALITY GATES
-----------------------------------------------
Before approving any Pull Request (PR), reviewers must systematically verify:
- Automated Test Coverage: New business logic must include automated unit tests achieving at least 80% line coverage.
- Error Handling: Expected error cases, network timeouts, and edge cases must be handled explicitly without generic catch-all blocks.
- Static Analysis: Zero warnings from Ruff, ESLint, or mypy static analyzers.
- Security Review: No hardcoded credentials, API keys, or raw SQL string concatenations.
- Database Migrations: Zero-downtime backward-compatible migrations must be reviewed by the Data Engineering squad.

3. REVIEWER CONDUCT AND COMMENT PREFIX CONVENTIONS
--------------------------------------------------
To maintain constructive feedback and clear intent, reviewers are encouraged to use standardized prefixes:
- [blocking]: Critical defect, test omission, or security flaw that must be addressed prior to approval.
- [nit]: Minor formatting or naming preference; author may choose to address or resolve without re-review.
- [question]: Inquiry seeking architectural rationale or clarification.
- [praise]: Affirmation of elegant solution design or exemplary test coverage.

4. TURNAROUND TIME SLA AND REVIEWER CONDUCT
-------------------------------------------
- Review Turnaround SLA: Reviewers must provide initial feedback or approval within twenty-four (24) business hours of PR submission.
- Constructive Tone: Critique the code, not the person. Suggest concrete alternatives and explain the technical rationale behind suggestions.
